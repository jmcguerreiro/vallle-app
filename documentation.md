# Vallle — project documentation

## What is Vallle?

Vallle is a vallle platform for local businesses. Stores sell branded physical postcards as gift vallles. Customers buy them in-store, write a personal message, and give them to someone. The recipient redeems the vallle at the store, partially or fully.

Vallle earns a flat **annual subscription fee per store**, tiered by how many vallles the store sells per year. Physical fulfilment (welcome pack, reprints, custom designs) is billed separately as one-off, cost-plus charges.

### How it works

1. Store owner logs into the Vallle app, creates a vallle, gets a unique code
2. Store writes the code and amount on a physical Vallle postcard, customer pays
3. Customer writes a personal message and gives the postcard as a gift
4. Recipient visits the store, presents the vallle at checkout
5. Store owner logs in, redeems the vallle (full or partial)
6. Remaining balance stays on the vallle until fully used or expired (configurable per company, default 1 year, max 5 years)

### Revenue model

Flat **annual subscription per store**, billed annually, tiered by the number of vallles the store **sells (issues) per year**. Prices are net (ex-VAT — B2B clients reclaim it; quote "+ IVA").

| Tier    | Vallles sold / yr | Price (net)              |
| ------- | ----------------- | ------------------------ |
| Starter | up to ~50         | €4.99/mo (billed yearly) |
| Growth  | ~50–300           | €12.99/mo                |
| Pro     | ~300–1,000        | €29.99/mo                |
| Custom  | 1,000+            | talk to us               |

- **Metric is count, not euro-volume** — physical fulfilment cost scales with card count, and count is simpler to reason about. Trade-off: a high-ticket seller pays the same as a low-ticket one at equal volume.
- **Tier assigned at renewal** — measure the past year's count, set the coming year's tier. Never bump mid-year (avoids threshold cliffs / gaming).
- **Free first year** — a store flagged `is_founding_member` has its first-year subscription waived (subscription only, not physical fulfilment). Granted quietly, case by case — no public program, not advertised.
- Replaces the old 5% commission model (see decision log, 2026-06-29).

### Onboarding & physical fulfilment

- Invite-only: you onboard each store manually
- Welcome pack at signup includes branded postcards + account setup
- Physical fulfilment is a **separate one-off, cost-plus line** — reprints, restocks (~€20–25 for 50), and custom designs. Never bundled into the subscription, never given away free (real COGS).
- Fulfilment orders (welcome packs and refills) are tracked per company, inside the company's modal (Admin → Companies): stores request by email/phone, the super_admin records the order, its items, price, payment, and fulfilment status. See **Fulfilment orders** below.

### Database: Cloudflare D1

D1 is SQLite at the edge. All monetary values stored as integers in cents (e.g. 5000 = €50.00) to avoid floating-point rounding.

IDs are ULIDs (sortable, time-based, shorter than UUIDs). Dates are ISO 8601 text strings (SQLite has no native datetime type).

#### Schema (v10) — 10 tables

```
users                   Who logs in (account-level: super_admin platform flag + active/inactive kill-switch)
stores                  Local businesses
store_users             Many-to-many membership + store-scoped role & status (admin/user, active/inactive access)
vallles                The core entity — created by stores, redeemed by recipients
redemptions             Each partial or full use of a vallle
subscription_periods    One row per store per billing year — the annual fee, with paid_at tracking
orders                  Physical fulfilment orders (welcome packs + refills), with paid_at tracking
order_items             What's inside an order (catalogue item + quantity)
password_reset_tokens   Time-limited tokens for password reset flow
auth_rate_limits        Fixed-window brute-force counters for the auth endpoints
```

**users** — `id`, `name`, `email` (unique), `password` (hashed), `role` (account-level — only `super_admin` is meaningful platform-wide; everyone else is `user`), `status` (account kill-switch `active`/`inactive`), `avatar` (default `paper-bag-head`), `locale` (`pt`/`en`, default `pt`), `created_at`, `updated_at`

**stores** — `id`, `name`, `slug` (unique), `category`, `email`, `vat_id`, `phone`, `address1`, `address2`, `city`, `postal_code`, `region`, `country` (default PT), `default_vallle_expiry_days` (default 365), `default_min_redemption_mode` (`none`/`full`/`custom`, default `none`), `default_min_redemption_cents` (default 0; only meaningful when mode is `custom`), `plan` (`starter`/`growth`/`pro`/`custom`, default `starter`), `plan_renews_at` (ISO date, nullable), `is_founding_member` (0/1), `status`, `created_at`, `updated_at`

**store_users** — `id`, `store_id`, `user_id`, `role` (store-scoped `admin`/`user`), `status` (store-scoped `active`/`inactive` — whether the user can access that store; default `active`), `created_at`. Unique constraint on (store_id, user_id). A user can be an admin in one store and a plain or inactive member in another — this is the source of truth for what a user can do within a store. (`suspended` is a store-level state on `stores.status`, not a membership one.)

**vallles** — `id`, `store_id`, `created_by` (user), `code` (6 chars stored raw, displayed as `XXX-XXX`, handwriting-friendly, unique per store via `UNIQUE(store_id, code)`), `amount`, `balance`, `buyer`, `status` (active/used/expired), `created_at`, `expires_at` (per-company default, max 5 years), `min_redemption_mode` (`none`/`full`/`custom`) and `min_redemption_cents` — the minimum-redemption policy, snapshotted from the store's defaults at creation (like `expires_at`) and editable per vallle, `updated_at`

**redemptions** — `id`, `store_id` (denormalised for fast queries), `vallle_id`, `redeemed_by` (user), `description`, `amount`, `balance_after` (snapshot), `created_at`

**subscription_periods** — `id`, `store_id`, `plan`, `period_start`, `period_end`, `amount` (net cents; `monthly × 12`, `0` for a founding member's free first year), `vallles_sold` (count snapshot that set the tier, computed server-side from the 365 days before `period_start`), `paid_at` (null = unpaid), `notes`, `created_at`, `updated_at`. Partial index on unpaid rows. The period history doubles as the subscription log: `created_at` = when the renewal was recorded, `paid_at` = when it was paid, `period_start`/`period_end` = what it covers, `notes` = free-form context. The store's `plan` and `plan_renews_at` mirror the latest period (`syncStoreFromPeriods` runs after every period write).

**orders** — `id`, `store_id`, `type` (`welcome_pack`/`refill`), `status` (`requested` → `preparing` → `shipped` → `delivered`; `cancelled` aborts), `amount` (net one-off price in cents; `0` = included, e.g. the welcome pack), `invoiced_at` (when the invoice was sent; null = still to invoice), `paid_at` (null = unpaid; mirrors `subscription_periods`), `notes`, `requested_at` (when the store asked — orders arrive by email/phone and may be recorded later, so it's editable and distinct from `created_at`), `created_at`, `updated_at`. The payment state is derived, never stored: `amount = 0` → included, no `invoiced_at` → to invoice, `invoiced_at` only → awaiting payment, `paid_at` → paid. Sequential — an order can't be paid before it was invoiced, enforced by a table `CHECK (paid_at IS NULL OR invoiced_at IS NOT NULL)` in addition to the API guards.

**order_items** — `id`, `order_id` (`ON DELETE CASCADE`), `item`, `quantity` (> 0). The item catalogue (`cards`, `envelopes`, `box`, `pen`) is validated in app code (`functions/api/admin/orders/_helpers.js`, mirrored in `src/constants/orders.js`), not a SQL CHECK, so adding a product is a constant edit rather than a migration.

**password_reset_tokens** — `id`, `user_id`, `token_hash` (SHA-256 of the raw token), `expires_at`, `used_at` (null = unused), `created_at`. Indexed on `token_hash` for fast lookup and `user_id` for invalidation. `ON DELETE CASCADE` on user_id.

**auth_rate_limits** — `bucket` (PK, `"<endpoint>:<client-ip>"`), `count`, `window_start` (ISO). Fixed-window counter backing the brute-force / abuse throttle on `login`, `forgot-password`, and `reset-password`. Written on every attempt via an atomic upsert; a bucket resets once `window_start` falls outside the endpoint's window. See `functions/api/_rate-limit.js`.

#### Password reset

Separate `password_reset_tokens` table. Raw token sent in email link, only SHA-256 hash stored in DB. Tokens expire after 30 minutes. On successful reset, all tokens for that user are marked as used. Supports multiple concurrent tokens (e.g. user requests reset on phone then laptop). Provides audit trail of reset attempts.

#### Vallle codes

6 alphanumeric characters, **stored raw** and **displayed grouped as `XXX-XXX`** (e.g. stored `XTUT6Q`, shown `XTU-T6Q`). The hyphen is purely presentational (`formatVallleCode` in `features/vallles/utils.js`): codes are stored and looked up without it, so it never participates in identity and there's no "typed with/without the dash" mismatch. Uses a 31-character alphabet excluding ambiguous characters (0/O, 1/I/L) to avoid handwriting confusion. Codes are **unique per store** (`UNIQUE(store_id, code)`), not globally — each store gets the full 31^6 ≈ 887M space to itself. On create, the insert retries with a fresh code if it hits a same-store collision (up to 5 attempts). Lookups are always store-scoped (`code` + `X-Store-Id`), so the same code can exist in two different stores.

#### Subscription billing

Stores pay a flat annual subscription, tiered by vallles sold/year (see **Revenue model**). No automated payment processor yet: the `subscription_periods` table is the fully manageable ledger _and_ log — one row per billing year. Billing management is company-centric — there is no standalone Subscriptions section or nav item. The company detail modal's Subscription accordion shows the current (latest) period (dates, payment state, amount, renewal date) with a full-width **Manage subscription** button opening the company's billing modal (`/admin/companies/:id/subscription`): the current period plus every past one (the log stays visible), with the full lifecycle:

- **Renew** (full-width button → `/admin/companies/:id/subscription/renew` → `POST /api/admin/subscriptions/periods`) — records the next billing year (or the first). The start is pre-filled with the current period's end (**paying early never shifts the anniversary**), the end with one year later, the plan with the suggested tier — the picker's help text explains it ("the suggested plan is X — the company sold N vallles in the last year") — and the amount with the plan's annual price (0 for a founding member's free first year). `vallles_sold` is snapshotted server-side from the 365 days before the period start.
- **Mark as paid** (`PATCH /api/admin/subscriptions/periods/:id`) — header action, shown only while the current period is unpaid; stamps `paid_at` = today, atomic.
- **Edit period** (header action for the current period; past rows click through too → `PUT /api/admin/subscriptions/periods/:id`) — adjust plan, amount, notes, and backfill or **clear** the paid date (corrects a mistaken mark-as-paid). The **start date is editable only on the company's first period** (`is_first` on the GET — every later start is anchored to the previous period), and moving it pulls the end along to one year later; the end date is always editable.
- **Delete** (`DELETE /api/admin/subscriptions/periods/:id`, on the Edit modal) — unpaid periods only, for rows recorded by mistake; a paid period is part of the payment log.

The companies list keeps its **Outstanding** column + unpaid/paid filter as the collection worklist.

After every period write the store's `plan` and `plan_renews_at` are re-synced from the latest period, so the company list/detail and the ledger can't drift; the `plan`/`plan_renews_at` fields on the company Create/Edit form remain as manual overrides. The tier is assigned at renewal, never auto-bumped mid-year. (The old 5% commission model — `commissions` table, `/api/commissions`, and the admin Commissions screens — was removed on 2026-06-29.)

#### Fulfilment orders

Physical goods tracking for the welcome pack (cards, envelopes, box, pen) and later refills. There is no client-facing ordering yet — stores request by email/phone and the super_admin records the order from the company's modal — but the schema is store-scoped and the API validation is shared, so a store-facing "request a refill" flow can reuse the same tables and helpers later. Like billing, orders are company-centric (no standalone Orders section or nav item): the company modal's Orders accordion is the worklist — pending orders only (anything not delivered, or delivered but still to invoice / awaiting payment; cancelled never counts), or an "all good" empty state when there's nothing to fulfil or chase — with a full-width **Manage orders** button opening the company's order log (`/admin/companies/:id/orders`): every order, rows opening the order detail, and an **Add order** button (the create form pre-selects the company via `?store=`). The order detail offers the next payment action in the modal header (`PATCH /api/admin/orders/:id` with `{ mark: "invoiced" | "paid" }`, atomic, same pattern as subscription periods). The payment record is two timestamps — `invoiced_at` (invoice sent) and `paid_at` — from which the API derives the state (`derivePaymentState` in `functions/api/admin/orders/_helpers.js`): **to invoice** → **awaiting payment** → **paid** (or **included** when `amount = 0`). The derived state is the single source of truth: it is returned as `payment_state` on every order payload — including the company detail's `orders` — so clients never re-derive it. The sequence is enforced at every layer: an order can't be marked paid before it was invoiced (`ORDER_NOT_INVOICED`, plus a table `CHECK`), and a paid order's invoice date can't be cleared; the invoice date is otherwise editable (and clearable) on the Edit form for backfilling. A sync test in `test/api/admin-orders.test.js` guards the client/server catalogue mirror. An order with `amount = 0` is "included" (e.g. the signup welcome pack) and never counts as owed. Fulfilment status is edited freely on the order's Edit form — no enforced state machine, matching how loose the real-world process is.

#### Expiry

Handled in app logic, not via cron. When a vallle is looked up, check `expires_at` against current time. If expired, treat as expired regardless of `status` field. No scheduled worker needed.

#### Minimum redemption

Discourages tiny redemptions (e.g. spending €1 at a time). Mirrors the expiry pattern: a store-level default (`stores.default_min_redemption_mode`/`_cents`) snapshotted onto each vallle at creation (`vallles.min_redemption_mode`/`_cents`) and overridable on the vallle's Edit screen. Three modes: `none` (any amount), `full` (the whole remaining balance at once), `custom` (at least `*_cents`). It is **advisory, not enforced**: the API does not reject below-minimum redemptions. The redeem screen surfaces a warn-and-confirm dialog (`useConfirm`) that the cashier can override — and redeeming the **entire remaining balance** never warns (covers "€5 left of a €20 purchase"). Frontend logic lives in `shouldWarnRedemption`/`formatMinRedemption` (`features/vallles/utils.js`); the form fields are the shared `components/forms/MinRedemptionFields.jsx`; modes are the `MIN_REDEMPTION_MODES` constant.

#### Production super admin

The production super admin is **not** committed to version control — it's
created once, by hand, against the remote database. Generate a real password
hash locally, then insert the row directly:

```bash
# 1. Generate a PBKDF2 hash for your chosen (strong) password.
#    Copy the "Hash:" value from the output.
node scripts/hash-password.js 'your-strong-password-here'

# 2. Insert the super admin into the remote DB. Paste the hash from step 1
#    in place of <HASH>. ULID can be any valid ULID (e.g. from an online
#    generator). joao@vallle.com is the production login email.
npx wrangler d1 execute vallle-db --remote --command="INSERT INTO users (id, name, email, password, role, status) VALUES ('<ULID>', 'João Guerreiro', 'joao@vallle.com', '<HASH>', 'super_admin', 'active')"

# 3. Verify (should return one row, role super_admin)
npx wrangler d1 execute vallle-db --remote --command="SELECT id, email, role, status FROM users WHERE role = 'super_admin'"
```

The plaintext password is never written to a file — only the hash is, and only
transiently in your shell history. Rotate it via the same flow if needed.

### 7. Testing

API tests run with **Vitest** via **`@cloudflare/vitest-pool-workers`**, which executes them inside the actual workerd runtime with a real (local, in-memory) D1 binding — no mocks for the database or Web Crypto.

```bash
npm test         # run once
npm run test:watch
```

How it fits together:

- **`vitest.config.js`** registers the `cloudflareTest` plugin pointing at `wrangler.toml` (so the `DB` binding exists) and defines test-only bindings: `JWT_SECRET` (a test value) and `TEST_MIGRATIONS` (the parsed migration files, excluding `0002_seed.sql` — tests seed their own fixtures).
- **`test/apply-migrations.js`** (setup file) applies the schema to the test D1 before each test file. The pool's **isolated storage** rolls every test's writes back automatically, so tests never see each other's data.
- **`test/_helpers.js`** provides fixture seeders (`seedUser`, `seedStore`, `seedMembership`, `seedVallle`, `seedStoreWithUser`), `buildRequest` (signs a real session JWT into the cookie + sets `X-Store-Id`), and `runRoute` — a minimal Pages Functions chain runner so routes are tested **through their real `_middleware.js`** (auth + store guards), not just the bare handler.
- Handlers are imported directly from `functions/` and invoked with a constructed context — the documented unit-testing pattern for Pages Functions (there's no `main` Worker, so `SELF.fetch` isn't available).

Coverage philosophy (pre-launch): test where bugs are expensive — money arithmetic (integer cents), redemption/expiry/status guards, and the auth/role/store-scoping rules. UI component tests and Playwright E2E are deferred until the product stabilises.

### Pages project (deployment)

This app deploys to **Cloudflare Pages**, not Workers. It uses the `functions/`
directory convention (Pages Functions) for the API — that is a Pages feature and
has no equivalent under a plain `wrangler deploy` Worker entry point. **Do not
deploy with `wrangler deploy`** (the Workers command) — it fails with "Missing
entry-point to Worker script or to assets directory" because there is no Worker
`main`. Use the Pages git integration (recommended) or `wrangler pages deploy`.

`wrangler.toml` sets `pages_build_output_dir = "dist"` so wrangler treats this as
a Pages project.

**Recommended — Pages git integration:**

1. Cloudflare dashboard → Workers & Pages → Create → **Pages** → Connect to Git,
   select this repo.
2. Build settings:
   - Build command: `npm run build`
   - Build output directory: `dist`
   - (No deploy command — Pages publishes `dist` and bundles `functions/`
     automatically.)
3. Settings → Bindings (D1 database bindings): bind `DB` → `vallle-db`.
4. Settings → Variables and Secrets (Production environment):
   - `JWT_SECRET` — **Secret**. Signs session tokens.
   - `RESEND_API_KEY` — **Secret**. Resend API key for password-reset email.
   - `ENVIRONMENT` — plaintext, set to `production`. Anything other than
     `development` makes session cookies `Secure`; `wrangler.toml` deliberately
     does **not** define it (the dev value lives in `.dev.vars`) so it can't leak
     into prod.

**Manual / CLI deploy:**

```bash
npm run build
npx wrangler pages deploy dist --project-name=vallle-app
```

> If the build log shows `Executing user deploy command: npx wrangler deploy`,
> the project was created as a **Workers** build, not Pages. Either recreate it
> as a Pages project (above), or change the build's deploy command to
> `npx wrangler pages deploy dist`.
